# GitHub Actions Dependency Locks

GitHub's workflow dependency locking public preview records the exact commits
behind direct and transitive action dependencies in
`.github/workflows/actions.lock`. ActionScope reads that file when it scans a
repository.

The authoritative format is maintained by
[`github/actions-lockfile`](https://github.com/github/actions-lockfile), and
the lockfile is generated by
[`gh actions-lock`](https://github.com/github/gh-actions-lock).

!!! warning "Public-preview format"

    The lockfile is pre-1.0 and may change. ActionScope currently accepts schema
    versions `v0.0.1`, `v0.0.2`, and `v0.0.3`. Unknown versions fail open: the
    scanner reports the parse error and continues treating mutable workflow
    references as unpinned.

## What ActionScope checks

For each workflow, ActionScope compares external `uses:` references with the
flat dependency list in `actions.lock`.

A mutable-looking reference such as `actions/checkout@v4` is considered locked
only when all of these are true:

1. The workflow appears in the lockfile's `workflows` map.
2. That exact `OWNER/REPO@REF` key appears in the workflow's dependency list.
3. The matching dependency entry contains a valid full `sha1-...` or
   `sha256-...` commit digest and the required repository identity fields.

Missing, malformed, or stale entries do not suppress unpinned-action findings.
ActionScope also checks every valid locked commit, including transitive
composite-action dependencies, against its known-compromised actions database.
A lock that resolves to a documented malicious commit produces a CRITICAL
finding.

Same-repository references beginning with `$/`, local `./` or `../` actions,
and Docker references are not matched against the GitHub Actions lockfile.

## Example

```yaml
version: v0.0.3
workflows:
  .github/workflows/ci.yml:
    - actions/checkout@v4
    - example/composite-action@v1
    - actions/cache@v4
dependencies:
  actions/checkout@v4:
    ref: v4
    commit: sha1-1111111111111111111111111111111111111111
    owner_id: 44036562
    repo_id: 197814629
  example/composite-action@v1:
    ref: v1
    commit: sha1-2222222222222222222222222222222222222222
    owner_id: 123
    repo_id: 456
    uses:
      - actions/cache@v4
  actions/cache@v4:
    ref: v4
    commit: sha1-3333333333333333333333333333333333333333
    owner_id: 44036562
    repo_id: 70474373
```

The terminal and Markdown reports show direct and transitive coverage. JSON
output includes a `dependency_locks` entry for every workflow:

```json
{
  "workflow_file": "/repo/.github/workflows/ci.yml",
  "schema_version": "v0.0.3",
  "status": "fully_locked",
  "direct_dependencies": 2,
  "locked_direct_dependencies": 2,
  "transitive_dependencies": 1,
  "uncovered_dependencies": []
}
```

Corpus scans write the same per-workflow measurements to
`workflow_locks.csv` and `workflow_locks.json`, using anonymized workflow IDs
by default.

## Coverage statuses

| Status | Meaning |
|--------|---------|
| `fully_locked` | Every external direct reference has a valid exact lock entry. |
| `partially_locked` | The workflow is listed, but one or more current references are missing or invalid. |
| `not_locked` | The workflow has external dependencies but no lock entry covers it. |
| `invalid` | An `actions.lock` file exists but its version or root structure could not be parsed safely. |
| `no_dependencies` | The workflow has no external action or reusable-workflow dependency. |

## What this does not prove

ActionScope performs offline static validation. It does not resolve the tag
again, prove when the lockfile was generated, or reproduce GitHub's runtime
owner/repository identity enforcement. Use `gh actions-lock` and GitHub's
runtime dependency locking to generate and enforce the file; use ActionScope
to include lock coverage and known-malicious commit checks in the broader
workflow security report.
